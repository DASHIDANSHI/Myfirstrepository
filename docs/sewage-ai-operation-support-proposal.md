## 1. 背景・目的

### 1.1 背景
- 下水処理場・ポンプ場では、流入水量・水質・DO・MLSS・ブロワ電力など多数の運転データ（SCADA/計装）が蓄積されている。
- 一方で、運転判断の多くはベテラン運転員の経験・暗黙知に依存しており、世代交代・技術継承が課題。
- 曝気（送風）は処理場電力の **40〜60%** を占め、運転最適化による省エネ・コスト削減の余地が大きい。

### 1.2 目的
生成AIと数値計算を組み合わせ、運転員の判断を **支援（advisory）** する仕組みを内製で構築する。
PoCでは「曝気（送風量）運転レコメンド」を対象に、**省エネ効果・安全性・現場の納得度** を検証する。

### 1.3 基本方針（安全性の前提）
- **自動制御は行わない。** AIは助言を出すのみで、最終判断・操作は必ず人が行う（Human-in-the-loop）。
- 誤提案が放流水質・コンプライアンスに直結するため、PoCは **シャドーモード**（提案を出すが実機に反映しない）から開始する。
- DO下限・放流基準などは **ハード制約** として数値エンジンに組み込み、制約違反の提案を出さない。

## 2. 全体アイデア（ユースケース一覧）

| # | ユースケース | 概要 | リスク | 位置づけ |
|---|---|---|---|---|
| 1 | ナレッジ対話（RAG） | SOP・運転日誌をAIに学習させ質疑応答 | 低 | 早期の見せ球 |
| 2 | 運転日報の自動生成 | 時系列データを要約し日報・特記事項を生成 | 低 | 将来拡張 |
| 3 | 異常アラームの説明 | 異常検知結果の原因推定・確認手順を提示 | 中 | 将来拡張 |
| 4 | **運転操作レコメンド** | 曝気・薬注等の最適化提案 | 高 | **本PoCの本命** |
| 5 | 流入量・水質予測 | 降雨連動で流入を先読み | 中 | 本命の構成要素 |
| 6 | what-if 相談 | 「大雨予報、どう備える？」等の相談相手 | 中 | 将来拡張 |

本PoCは **#4 運転操作レコメンド（曝気）** を本命とし、その構成要素として **#5 流入予測**、見せ球として **#1 ナレッジ対話** を併用する。

## 3. PoC対象：曝気（送風量）運転レコメンド

### 3.1 なぜ曝気か
- 処理場電力の 40〜60% を占め、省エネ効果＝コスト効果を定量化しやすい。
- DO・MLSS・流入量と物理的因果が明確で、提案の妥当性を検証しやすい。
- 放流水質（BOD/NH4-N）への影響を追跡でき、安全性評価が可能。
- KPIが「送風電力量の削減率（%）」と明快で、PoCの成否判定が容易。

### 3.2 KPI（合否基準）
1. **省エネ効果**：バックテストで送風電力 ○% 削減を試算（目標値はフェーズ0で合意）。
2. **安全性**：提案がDO下限／放流基準を割らない（制約違反ゼロが必須）。
3. **説明の納得度**：ベテラン運転員による提案カード評価（5段階 × N件）。
4. **採用率**：シャドー運用で運転員が「採用したい」と答えた割合。

## 4. アーキテクチャ

### 4.1 役割分担（設計の核心）
数値の最適値は **LLMに計算させない**（ハルシネーション・不安定性のため）。
LLMは数値エンジンの結果を **説明・対話・SOP照合** する役に徹する。

```
[データ層]
 SCADA時系列(流量/DO/MLSS/水温/送風量/電力) ─┐
 運転日誌・SOP(文書)                          ┼→ 前処理 → スプレッドシート蓄積
 気象・降雨(オプション)                        ┘
        │
        ▼
┌─────────────────────────────────────────────┐
│ ① 数値エンジン（"計算"担当）                  │
│   ・流入/負荷の短期予測（1〜3h先）            │
│   ・DO目標を満たす必要送風量を推定            │
│   ・SOPのハード制約（DO下限・放流基準）を適用  │
│   → 推奨送風量 ＋ 根拠データ                   │
└─────────────────────────────────────────────┘
        │ 推奨値＋根拠
        ▼
┌─────────────────────────────────────────────┐
│ ② 生成AI/LLM（"説明・対話"担当）              │
│   ・①の結果＋該当SOPを統合してプロンプト化     │
│   ・「なぜこの提案か」を日本語で言語化         │
│   → 提案カード（推奨/理由/リスク/確認項目）    │
└─────────────────────────────────────────────┘
        │
        ▼
[③ 運転員] 採用・却下・修正（自動制御なし）
        │
        ▼
[④ フィードバック] 採否と結果を記録 → 改善
```

## 5. 数値エンジン（①）の設計

### 5.1 予測対象
曝気で効くのは流量そのものより **酸素要求量**。その駆動因子を予測する。

| 予測対象 | 必要性 | 取得性 |
|---|---|---|
| 流入水量 Q | 滞留時間・送風量のベース | SCADAで容易 |
| 流入負荷（BOD/COD） | 有機物酸化の酸素要求量 | 連続計がなければQと相関で代理 |
| アンモニア性窒素 NH4-N | 硝化の酸素要求量（高度処理で重要） | NH4計があれば直接 |
| 水温 | 硝化速度・酸素溶解度に影響 | SCADAで容易 |

実務では **流入水量Qの予測から開始** し、負荷は「Q × 水質の日内パターン」で近似 → 水質連続計があれば精緻化。

### 5.2 説明変数（予測のもと）
1. 過去の流入パターン（日内・曜日・季節変動）＝主役
2. 時刻・カレンダー特徴量（時刻・曜日・祝日）
3. 上流ポンプ場の流量／水位（管路移動時間による自然のリードタイム）
4. 降雨データ（合流式では決定的、分流式では影響小）
5. 水温

### 5.3 予測ホライズン
反応槽のプロセス時定数（HRT）から決める。

| ホライズン | 用途 |
|---|---|
| **1〜3時間（本命）** | 曝気・送風量の先行調整、DOの振れ防止 |
| 〜6時間 | ピーク到来への備え、台数制御の計画 |
| 〜24時間 | 翌日の運転計画・要員配置・薬品手配 |

PoCは **1〜3時間先（粒度15分〜1時間）** をコアとし、フィードフォワード制御で省エネを狙う。

### 5.4 予測手法（難易度3段階）
| レベル | 手法 | 工数 | PoCでの扱い |
|---|---|---|---|
| 1 | 曜日×時刻平均 ＋ 直近補正 | 数日 | **出発点（ベンチマーク）** |
| 2 | 勾配ブースティング（LightGBM 等） | 1〜2週 | **本命（環境が許せば）** |
| 3 | 深層学習（LSTM/Transformer） | 数週〜 | PoCでは原則不要 |

**進め方**：レベル1で土台を作り「どこまで当たるか」を基準化 → レベル2で上回るか検証 → 十分なら提案カード化に注力。
真の難所はアルゴリズムではなく **データ整形・評価設計・現場接続** にある（後述リスク参照）。

## 6. SOPの扱い（②の知識源）

### 6.1 SOPに定められている想定内容
1. 通常運転の操作基準（DO目標、MLSS範囲、送風量・薬注の基準、汚泥引抜き）
2. 時間帯・季節・負荷変動への対応ルール
3. 異常時・非常時の対応手順（バルキング、水質急変、降雨/CSO、機器故障）
4. 監視・記録・判断の基準（点検頻度、報告・エスカレーション、放流水質基準）
5. 安全・保全に関する手順

### 6.2 SOPは「制約」と「知識」の二役
| 使い方 | 抽出するもの | 実装での扱い |
|---|---|---|
| **ハード制約**（守らせる） | DO下限・放流基準・MLSS範囲などの数値しきい値 | ①数値エンジンに制約として組込み |
| **ソフト知識**（説明・対話） | トラブル対応手順・判断背景・運用ノウハウ | ②LLM＋RAGの参照 |

PoC初期工程で、SOPから **「管理項目・目標値・上下限・対応条件・参照元」を構造化テーブル** に抜き出す。
これは暗黙知の形式知化でもあり、AI抜きでも価値が出る。

## 7. 内製環境への割り付け

### 7.1 利用可能な環境
- Google Workspace（Google Apps Script / スプレッドシート 等）
- Gemini（Workspace内）、NotebookLM
- **制約**：Gemini API は利用不可
- **代替**：別の社内AIツールのAPIが利用可（モデル選択可能）

### 7.2 ツール割り付け
| スキーム要素 | 使用ツール | 補足 |
|---|---|---|
| ① 数値エンジン（レベル1） | スプレッドシート ＋ Apps Script | 追加環境なしで完結 |
| ① 数値エンジン（レベル2） | Google Colab or BigQuery ML | 利用可否は要確認 |
| ② LLM（提案カード生成・対話） | 社内AIツールAPI | GAS `UrlFetchApp` から呼出。Gemini API代替 |
| SOPナレッジ対話（手動探索） | NotebookLM | 文書を入れるだけでRAG。即戦力の見せ球 |
| データ蓄積・フィードバック記録 | スプレッドシート | 採否ログもここ |
| 可視化・提案カードUI | スプレッドシート / GASウェブアプリ / Looker Studio | 運転員が見る画面 |
| 資料作成・アドホック分析 | Workspace Gemini | 設計補助 |

**Gemini APIが不可でも、②のLLM役は社内AIツールAPIが丸ごと担えるため達成可能。**

### 7.3 NotebookLM と 自動提案カードの住み分け（重要）
NotebookLMは **人が画面で対話するインタラクティブツール** であり、自動パイプラインへの組込みは想定しない。

| | A. 手動ナレッジ探索 | B. 自動の提案カード生成 |
|---|---|---|
| ツール | NotebookLM（手動） | 社内AI API ＋ 自前の軽量RAG |
| 計算結果の扱い | 人が必要に応じて貼付 | GASが自動でプロンプトに同梱 |
| 位置づけ | 知識の壁打ち・見せ球 | 運転レコメンドの本体 |

- **本命（B）では人の手入力は不要。** GASが計算結果とSOP該当箇所を1つのプロンプトにまとめ、社内AI APIへ自動送信する。
- ここでの「軽量RAG」は大げさなものではなく、**SOP構造化テーブル（スプレッドシート）から該当行をGASが引いてプロンプトに差し込む** だけでよい。ベクタDBは不要。

#### 自動プロンプトの組み立てイメージ
```
【現在の状況】流入量 8,200 m³/h、DO 1.2 mg/L、水温 18℃
【数値エンジンの推奨】2時間後に流入増加見込み。
                     送風量を 4,500→5,200 Nm³/h に先行増加を推奨
【関連SOP（自動抽出）】
 ・好気部DO管理目標: 1.5〜2.5 mg/L
 ・流入増時は送風を先行調整、DO下限1.0を割らないこと
→ 上記をもとに、運転員向けに「推奨/理由/注意点/確認項目」を
   日本語の提案カードにまとめてください
```

### 7.4 内製・現環境版 構成図
```
[データ] SCADA出力(CSV/Excel) → スプレッドシート
            │
[① 数値]  GAS/シート関数で 曜日×時刻平均＋直近補正 → 推奨送風量＋根拠
            │（必要送風量・DO目標・制約チェック）
            ▼
[② 説明]  GAS → 社内AIツールAPI で提案カードを文章化
          SOP参照は シートのSOPテーブル（自動）／NotebookLM（手動）
            │
[UI]      スプレッドシート or GASウェブアプリに提案カード表示
            │
[運転員]  採用/却下/修正 を記録 → シートに蓄積（フィードバック）
```

## 8. 評価設計

1. **省エネ効果**：過去データで「AI提案通り運転していたら」を **バックテスト**（シャドーモード）→ 送風電力削減率を試算。
2. **安全性**：提案がDO下限／放流基準を割らないか（制約違反ゼロが必須）。
3. **説明の納得度**：運転員による提案カード評価（5段階 × N件）。
4. **採用率**：シャドー運用で「採用したい」と答えた割合。

PoCはまず **シャドーモード**（提案を出すが実機に反映しない）で回し、安全と効果を確認してから実運用承認フローへ進む。
評価では **未来情報の漏洩（リーク）を防ぐバックテスト設計** を徹底する。

## 10. リスクと対策

| リスク | 対策 |
|---|---|
| 誤提案リスク | 自動制御せず人間承認必須。DO下限等を数値エンジンにハード制約として組込み |
| LLMのハルシネーション | 数値はLLMに生成させず①の結果を引用。SOP出典を明示 |
| データ品質（欠測・センサドリフト） | フェーズ0で評価。不足なら対象範囲を縮小 |
| 現場の受容性 | 早期から運転員を巻き込み「置き換え」でなく「支援」と位置づけ |
| レベル2ML環境の制約 | Apps Scriptでは本格ML不可。Colab/BigQuery可否を確認。不可ならレベル1で完結 |
| NotebookLMの自動連携不可 | 自動経路は社内AI API＋シートRAGで構成。NotebookLMは手動探索に限定 |

## 11. 未決事項（要確認）

1. PoC対象処理場と処理方式（標準活性汚泥法 / OD法 / 高度処理）— HRT・予測対象・最適ホライズンに影響。
2. 排除方式（分流式 / 合流式）— 合流式なら降雨予測の作り込みが必須。
3. 上流ポンプ場の流量・水位データの取得可否 — 予測精度を大きく左右。
4. Google Colab または BigQuery の利用可否 — レベル2MLの実装可否を決定。
5. SOPの文書化レベルと標準化状況（処理場ごとにバラバラ / 標準雛形あり）— 横展開設計に影響。
6. 省エネ効果のKPI目標値（送風電力削減率の目標）。
